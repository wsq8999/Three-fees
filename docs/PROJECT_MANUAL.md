# 智能物业管理系统项目手册

本文件是项目的统一事实源。所有角色开始工作前必须阅读，完成工作后必须同步更新各自报告；架构、接口或数据模型发生变化时，必须同步更新本手册。

## 1. 项目目标

面向江苏省物业审计业务搭建可试运行的前后端系统：以 Java/MySQL 为业务事实源，覆盖登录与市域权限、四类月度数据导入、计费点与审计分析、AI 报告草稿、正式报告、历史报告、修正、日志和 Windows 部署。现有 AI DEMO 仅作为能力参考，敏感材料、依赖目录、数据库实现和密钥均不得直接复制。

## 5. 架构决策

### 5.1 仓库结构

```text
backend/          Java 21 / Spring Boot 模块化单体
frontend/         Vue 3 / TypeScript 单页管理端
ai-service/       无状态、内网可见的 Python AI 原子能力
contracts/        OpenAPI、AI JSON Schema、导入字段元数据
deploy/windows/   IIS、WinSW、PowerShell 部署与备份脚本
docs/             手册、ADR、角色报告与运行说明
```

### 5.2 后端

- Java 21、Spring Boot 4.1、Maven Wrapper、Spring Web/Validation/Security、Spring Session JDBC、MyBatis、Flyway、Actuator、springdoc。
- 单体按业务特性分包：`identity`、`organization`、`importing`、`billingpoint`、`audit`、`dashboard`、`report`、`ai`、`file`、`operationlog`。
- 特性内部使用 `api/application/domain/infrastructure`；禁止建立无边界的 `common` 或 `utils` 杂物包。
- 不使用 Lombok；DTO、领域模型和持久化对象边界明确。

### 5.3 前端

- Node 24 LTS、pnpm 11.9、Vue 3、TypeScript strict、Vite、Element Plus、Pinia、Vue Router、ECharts。
- 页面按路由懒加载；业务特性、共享组件、API 与状态分层；不在 `localStorage` 保存会话令牌。
- 以需求原型为信息架构依据，优先完成 1366×768 管理端；保留合理响应式下限。

### 5.4 数据库、任务与文件

- 生产目标 MySQL 8.4 LTS；迁移 SQL 同时兼容本机 MySQL 8.0.31。
- 当前不引入 Redis、外部消息队列、对象存储、微服务或容器编排。
- 慢任务使用 MySQL 持久化任务表；提交返回 `202 Accepted`，工作进程可恢复、可重试且要求幂等。
- 文件存储在仓库外的 ACL 保护目录，数据库仅记录元数据、SHA-256 和业务关联。

### 5.5 AI 边界

- Java/MySQL 是唯一业务事实源，负责用户、权限、任务、审计、报告和状态机。
- Python sidecar 不访问 MySQL，只提供文档解析、事实提取、原因判断、报告组织和纠错理解等原子能力。
- Python 运行基线为 3.12；`pyproject.toml` 允许 3.12–3.14，但未在某版本完成全套验证前不得把它写成生产基线。
- 内部接口绑定回环地址，使用服务令牌；请求包含契约版本、工作流版本、任务 ID、幂等键、输入摘要和 trace ID。
- 外部模型仅接收最小必要、脱敏/假名化的数据；当前默认使用假模型验证，不调用真实付费 API。

### 5.6 业务口径

- 当前数据月份：四类数据均存在成功且激活批次的最新完整自然月。
- 计费点主数据按计费点编码唯一；月快照按计费点编码 + 年月唯一。
- 四类任一激活批次变化均触发重新计算；旧批次保留并标记被替代，不物理删除。
- 实际总电量取有效电表行的“分摊后度数”之和；缴费明细审核状态决定是否具备参与资格。
- 正式报告按计费点 + 期间唯一；修正保留报告编号并覆盖当前正式内容，仅留审计元数据和摘要，不保留旧正式文件版本。

### 5.7 Windows 服务当前状态

- `three-fees-api` 与 `three-fees-ai` 配置为自动启动；AI 仅绑定 `127.0.0.1:8100`。
- `three-fees-worker` 的进程角色与部署模板已建立，但第一阶段尚无持久任务消费者/常驻循环，因此固定为 `Manual` 且安装时不启动，避免正常退出后被反复拉起。
- 只有 durable task consumer、租约、重试和重启恢复测试完成后，Commander 才能批准 worker 改为自动启动。

### 5.8 备份与恢复当前状态

- 仓库已提供 MySQL + 文件的一致时间窗备份、7 个日备 + 4 个周备轮转、隔离恢复演练、健康检查和 RPO/RTO 验收脚本；所有写入默认 dry-run 或要求显式 `-Apply`。
- 当前一致性模式固定为 `Quiesced`：必须由外部维护流程提供覆盖数据库快照和文件复制全过程的有效停写标记。
- 在文件模块证明“临时写入、校验、原子落盘、不可变、数据库最后提交引用、备份期间不物理删除”并由 Commander 批准前，禁止开启 `AppendOnlyFileContractApproved`。
- 仓库模拟验收不等于生产灾备验收；真实 Windows Server、MySQL 8.4 和全量数据的隔离恢复必须在预生产证明 RPO 24 小时、RTO 4 小时。

## 6. 工程与编码规范

- 仓库统一 UTF-8、LF、末尾换行；通过 `.editorconfig` 和 `.gitattributes` 固化。
- Java 使用 Spotless、Checkstyle、Maven Enforcer、JaCoCo；前端使用 ESLint、Prettier、Stylelint、Vitest、Playwright。
- 行为变更遵循 RED → GREEN → REFACTOR；配置/原型必须先写验收条件，再记录可重复验证命令。
- 所有环境配置从环境变量读取；仓库只提交 `.env.example`，不得提交真实值。
- 日志使用结构化字段并携带 `traceId`；不得记录口令、令牌、模型原始敏感输入。

## 7. RESTful API 规范

- 公共前缀：`/api/v1`；资源使用复数名词和 kebab-case，JSON 字段使用 camelCase。
- `GET` 查询、`POST` 新建/提交、`PUT` 全量替换、`PATCH` 局部修改、`DELETE` 删除/停用；不得用路径动词模拟资源。
- 创建返回 `201 Created` 和 `Location`；异步提交返回 `202 Accepted` 和 `Location`；删除成功返回 `204 No Content`。
- 不使用统一 `Result<T>` 成功包裹；分页统一 `{items,page,size,totalElements,totalPages}`。
- 错误使用 RFC 9457 `application/problem+json`，扩展 `code`、`traceId`、`fieldErrors`。
- 金额、度数等高精度十进制在 JSON 中使用字符串；日期/时间使用 ISO 8601。
- 写操作按需支持 `Idempotency-Key`；并发编辑使用 `ETag`/`If-Match`。

## 9. 安全规则

- 同源 SPA 使用 HttpOnly、Secure（生产）、SameSite 会话 Cookie；启用 CSRF 防护。
- 角色为 `SUPER_ADMIN`、`CITY_USER`；地市数据范围必须在后端 SQL/应用服务中强制执行，不能依赖前端隐藏。
- 登录限制、上传类型/大小/压缩炸弹防护、提示词注入防护和证据白名单必须逐步落地。
- 所有账号使用用户指定的统一临时初始口令，但数据库和仓库只保存自适应哈希；正式上线前启用首次登录改密。
